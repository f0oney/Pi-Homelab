As MKDocs is running in a container, `mkdocs gh-deploy` needs to be run inside the container. This is done with `docker exec`, followed by the container name (`mkdocs`, as set by `container_name` in the compose file) and the command itself:

```bash
docker exec mkdocs mkdocs gh-deploy
```

The container authenticates with GitHub through the host's SSH agent, which is set up in **1. Installation for MkDocs** (SSH Agent Setup and Docker Compose File). Complete those sections before continuing.

### Check the Repository Remote
`gh-deploy` pushes to whichever remote the repository uses. For the SSH agent to be used, the remote must be an SSH URL (`git@github.com:...`) rather than HTTPS. On the host, from the repository folder:

```bash
cd ~/pihomelab
git remote -v
```

If it shows an `https://` URL, switch it to SSH:

```bash
git remote set-url origin git@github.com:<username>/<repo>.git
```

The container only sees the folder mounted at `/docs` (`MKDOCS_VOLUME`, i.e. `~/pihomelab`). As this is the repository root, the `.git` folder is included and the container can find the repository. If `MKDOCS_VOLUME` is ever pointed at a sub-folder instead, `gh-deploy` will fail with `not a git repository`.

### Check the Host SSH Agent
Confirm the agent is running and holds your key. After a reboot, the key needs to be added again:

```bash
ssh-add -l
ssh-add ~/.ssh/id_ed25519   # only if no key is listed
```

### Verify the Container Can See the Agent
Confirm the `known_hosts` file and the agent socket are mounted, and that the agent is reachable from inside the container:

```bash
docker exec mkdocs ls -la /root/.ssh /ssh-agent-dir
docker exec mkdocs ssh-add -l
```

The second command should list the same key as on the host.

### Test GitHub Authentication Inside the Container
Verify that the container can authenticate against GitHub using the agent:

```bash
docker exec mkdocs ssh -T git@github.com
```

_Expected response:_ `Hi username! You've successfully authenticated, but GitHub does not provide shell access.`

### Deploy the Documentation
Build the site and push it to the repository's `gh-pages` branch:

```bash
docker exec mkdocs mkdocs gh-deploy --force
```

`--force` overwrites the `gh-pages` branch with the new build. This is safe as long as nothing else commits to that branch. `gh-deploy` also adds the `.nojekyll` file to the branch automatically, so GitHub Pages serves the built HTML as-is.

Only the `docs` folder is built into the site, so `.env` and `mkdocs-compose.yaml` are not published to GitHub Pages. They are still part of the repository itself, which is why `.env` is listed in `.gitignore` (see **1. Installation for MkDocs**).

### Configure GitHub Pages
This only needs doing once. In the repository on GitHub, go to **Settings → Pages**, and under **Build and deployment** set:
- **Source:** Deploy from a branch
- **Branch:** `gh-pages`, folder `/ (root)`

The site will be published at `https://<username>.github.io/<repo>/` after a short delay.

### Troubleshooting
**`fatal: detected dubious ownership in repository at '/docs'`**

The container runs as root, while the files belong to your user on the host, so Git refuses to use the repository. Mark the folder as safe inside the container:

```bash
docker exec mkdocs git config --global --add safe.directory /docs
```

This setting is lost when the container is recreated (e.g. after an image update), so re-run it if the error returns.

**`Permission denied (publickey)`**

The container can't reach the agent, or the agent has no key loaded. Re-run the checks in "Check the Host SSH Agent" and "Verify the Container Can See the Agent". If `ssh-add -l` works on the host but not in the container, recreate the container so it picks up the agent folder mount:

```bash
cd ~/pihomelab
docker compose -f mkdocs-compose.yaml up -d --force-recreate
```
